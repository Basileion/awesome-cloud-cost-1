# Contributing to Awesome Cloud Cost

Thank you for your interest in contributing! This document provides guidelines for contributing to this awesome list.

## How to Contribute

1. **Fork the repository**
2. **Create a new branch** for your contribution
3. **Make your changes** following the guidelines below
4. **Submit a pull request** with a clear description

## Contribution Guidelines

### What to Include

This list focuses on:
- Cloud cost management and optimization tools
- FinOps platforms and practices
- Cost visibility and monitoring solutions
- Open-source cost management projects
- Educational resources and best practices
- Tools for AWS, Azure, GCP, and multi-cloud environments

### Quality Standards

✅ **Include if:**
- Tool is actively maintained (updated within last year)
- Has clear documentation or README
- Provides real value for cloud cost management
- Open-source OR commercial with free tier/trial
- Serves a specific purpose in cloud cost optimization

❌ **Exclude if:**
- Abandoned or unmaintained (2+ years without updates)
- Closed-source without any free access
- Primarily promotional content
- Duplicate of existing entry
- Not related to cloud cost management

### Formatting Rules

Follow this exact format:
```markdown
- **[Tool Name](https://example.com)** - Brief description of what it does and key features.
```

**Good example:**
```markdown
- **[Kubecost](https://www.kubecost.com)** - Real-time Kubernetes cost monitoring, optimization, and governance.
```

**Bad examples:**
```markdown
- [Tool] - helps with cloud costs (too vague)
- **Tool Name** - The best and most amazing tool ever! (too promotional)
- Tool Name - does stuff (missing link, wrong format)
```

### Description Guidelines

Descriptions should be:
- **Concise**: One sentence, maximum two
- **Informative**: Clearly explain what the tool does
- **Objective**: Factual, not promotional
- **Specific**: Highlight key features or unique capabilities

### Pull Request Process

1. **Search first**: Ensure the tool isn't already listed
2. **One tool per PR**: Makes review easier
3. **Descriptive title**: Use format "Add [Tool Name] to [Category]"
4. **Description**: Explain why this tool should be included
5. **Test links**: Ensure all URLs work correctly
6. **Maintain order**: Keep alphabetical within sections when possible

### PR Title Examples

Good titles:
- `Add Kubecost to Kubernetes Cost Management`
- `Update CloudHealth description`
- `Fix broken link for Infracost`
- `Add FinOps certification resources`

### PR Description Template
```markdown
## What
Brief description of what you're adding/changing.

## Why
Explain why this addition is valuable.

## Checklist
- [ ] Entry follows formatting guidelines
- [ ] Link works and points to official source
- [ ] Description is concise and accurate
- [ ] Entry is in appropriate category
- [ ] No duplicate entries exist
- [ ] Tool meets quality standards
```

### Updating Existing Entries

When updating:
- Fix broken links promptly
- Update descriptions if tools have major changes
- Mark deprecated tools appropriately
- Preserve original intent unless incorrect

### Removing Entries

Tools should be removed or marked if:
- Project is archived/abandoned (2+ years)
- Website/repository no longer accessible
- Tool has been superseded
- Major unresolved security issues

Consider marking instead of removing:
```markdown
- ~~**[Old Tool](link)**~~ - **[Deprecated]** Description. Replaced by [New Tool](link).
```

## Style Guide

### Capitalization
- Tool names: Use official capitalization
- Descriptions: Standard sentence case
- Acronyms: All caps (AWS, GCP, API, ML, AI)

### Links
- Use official website or main repository
- Prefer HTTPS when available
- No trailing slashes unless required
- Link to product pages, not blog posts

### Punctuation
- End descriptions with a period
- Use Oxford commas
- Use em dashes (—) for parentheticals

## Content Guidelines

### For Commercial Tools
- Must have free tier, trial, or freemium model
- Clearly state if enterprise-only pricing
- Focus on features, not pricing

### For Open Source Tools
- Must have active repository
- Should have clear documentation
- Note license type if relevant

### For Resources
- Must be publicly accessible
- Current and maintained
- High quality and reputable sources

## Review Process

Maintainers will review PRs for:
1. **Relevance** - Is it cloud cost-related?
2. **Quality** - Does it meet standards?
3. **Formatting** - Follows guidelines?
4. **Uniqueness** - Not a duplicate?
5. **Accuracy** - Description correct?

Reviews typically take 1-7 days. Please be patient and responsive to feedback.

## Questions?

- Check existing issues for similar questions
- Open a new issue with "question" label
- Be specific and provide context

## Code of Conduct

Be respectful, constructive, and professional. We're building this resource for the cloud community.

## Recognition

Contributors will be acknowledged in the repository. Thank you for helping make cloud cost management more accessible!
